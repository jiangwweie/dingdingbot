既有持仓保护和退出沿冻结 Ticket 执行，所有当前暂停权限保持。

Owner 已复核通过并明确要求开始实施，**部署前须等待 Owner 单独确认**。
复核通过并进入实施阶段后，由当前任务主代理顺序推进已授权步骤；不为每个测试或普通实现步骤重复请求批准。
不创建新聊天，不默认并行修改共享 Kernel／数据库边界。

生产现状、精确发布身份及阶段结果只记入[主路线图](../../current/MAIN_CONTROL_ROADMAP.md)。

## 4. D0～D2：先固定身份和唯一权威

### D0 启动

1. 检查本线程修复／认证／部署进度与真实进程，防重入；检查工作区与相邻任务修改。
2. 使用当前部署只读脚本刷新 Policy、runtime、schema、Owner 控制和未决对象；PG 使用显式 READ ONLY、5 秒超时及有界查询。
3. 复核设计中的 2.0%～3.0%、0.1 步长、账户级作用范围等待复核选择；不得默默增加 1% 或 5% 档位。
4. 明确部分 TP1 缺陷当时是否仍存在及其独立处理状态；不将手动全平成功视为该缺陷修复。
5. 创建 focused `codex/*` 实现分支；实施开始前才执行此动作，本轮不创建实现分支。

### D1 权威模型及前向迁移

- 在现有 Policy 中保存唯一有效 r 及派生值，复用 Owner 变更 Journal／Current 模式保存 pending。
- 固定规则版本、公式摘要、允许范围和 step；方向控制绑定公式并保留 view。
- 为请求保留源 Policy／方向版本、目标 r、幂等键、Owner、原因和 requested/effective 时间；认证信息只存安全引用。
- 迁移必须验证精确来源并保持 2%／6%／4%／50%，注册能力不等于风险上调。
- 保留历史规则、Policy events、Ticket／Claim／Review；历史只作记录，不开发旧新运行时兼容分支。
- 数据库约束验证派生恒等式、合法 precision 和版本；最小授权只允许官方变更路径。
- 迁移编号依据开始实施时的实际最新 revision 确定；不得修改已执行历史迁移来冒充升级。

### D2 原子变更

- 实现“预览无写入、提交重新验证、同 key 幂等、CAS 冲突明确、同值无操作”。
- 有效 Policy、绑定与 effective 回执同事务提交；失败完整回滚。
- 修改保留 Owner pause、Family、风险容差、Selection、杠杆等非目标字段。
- 数据库控制读失败不回退默认；重启不把 Owner 后续选择重置为 2%。
- 参数请求与 view 切换冲突时明确拒绝本次请求并返回有效状态，不后台覆盖先前请求。

## 5. D3：发送和生效的必测顺序

**先绘出并测试现有 final-send 协调点，再接入参数控制；不能凭“已有锁”断言无竞态。**

| 切点 | 操作交错 | 预期结果 |
| --- | --- | --- |
| Claim 前 | 变更请求先提交 | 暂不签发，完成切换后按新值处理仍有效的自然信号 |
| Ticket 后、最终授权前 | 已有旧 Ticket | 正式终结未发送命令并释放资源，不改冻结数量、不重新发 ENTRY |
| 最终授权后、网络前 | 旧命令获权 | 请求 pending；精确归属旧版，结果闭合前不宣称新版本 effective |
| 网络结果未知 | 发送成功但响应丢失 | 对账确切身份，不重发；pending 不自动当失败清除 |
| 授权持有者暂停后恢复 | 进程延迟至授权过期 | 原发送窗口检查拒绝迟到执行；必须证明恢复协议不会遗留旧授权 |
| 生效事务中崩溃 | Policy 与回执写一半 | 全部回滚或全部提交，读取结果唯一 |
| 与 Owner pause 并发 | pause 在请求后生效 | 新风险值可落地，但 ENTRY 保持暂停 |
| 与方向切换并发 | 两请求竞争同版本 | 排序或明确冲突，不组合成未确认的 r/view |
| 有保护仓位时下调 | 存量大于新上限 | 保护／退出继续；新增按新总额／方向预算限制 |

使用真实本地 PostgreSQL、异步屏障与 Recording Venue；不伪造生产时钟、Signal、Ticket，不靠真实测试订单验证。
Worker 重启后继续持久化 pending；使用已有驻留进程的有界调度，不引入新定时器或常驻服务。

## 6. D4：前端可复核交付

1. 风险预算卡片显示唯一可编辑 r 和只读联动值；使用业务措辞而非内部数据库状态。
2. 保存前显示旧新值、最低实现门槛、作用账户和存量超限提示；金额标注余额采样时间，陈旧时降级为比例显示。
3. 复用二次认证、同源防护和现有组件；验证非法输入、重复点击、刷新、断网与版本冲突。
4. pending 同时显示当前和目标；只在后端 effective 后展示新有效值。
5. 保持既有方向选择操作；切换风险值后矩阵和预算展示刷新，读写两端都采用同一公式版本。
6. 旧 Owner API 与新 Kernel 不能混跑控制写入；上线流程验证独立 API 和静态前端身份。

## 7. D5：验收矩阵与测试等级

| 验收组 | 必须覆盖 | 通过标准 |
| --- | --- | --- |
| 公式 | 2%、2.5%、3%、各方向、unset | total=3r、base direction=2r、minimum=0.5r，旧 view 保留 |
| 数量／名额 | 三笔混合方向满额、第三笔同向、Family／同策略限制 | 满额仅在全部门槛满足时允许，原有限制不被绕过 |
| 金额／取整 | 保证金封顶、窄止损、最低门槛等值／差一个 step | Decimal 精确结果；不得为通过测试放宽门槛 |
| 审计／安全 | 幂等、CAS、权限、TOTP、错误 payload | 无非法写入、无秘密输出、版本及来源可追溯 |
| 切换／恢复 | 第 5 节全部交错 | 无迟到旧版发送、无重复 ENTRY、存量保护连续 |
| 迁移／认证 | 初装、重复安装、源漂移、已修改后重启 | 初次 2%；后续保留 Owner 值；历史不变；漂移明确阻断 |
| 前端／接口 | 预览、pending、结果丢失、冲突、范围说明 | 显示与后端权威一致，未生效不显示成功 |
| 回归 | Directional V1、Owner pause、发送窗口、结算／复盘 | 原有约束与历史经济语义不改变 |

测试按 **focused RED/GREEN → 受影响回归与审查 → 唯一最终候选 Release Certification** 执行。
测试环境先修环境，不弱化断言；不在每次小改后跑全套正式认证。
本地 3% 测试证明软件能力，不授权上线后自动把 Owner 的 2% 调成 3%。

## 8. D6：首次发布与保全

**最高等级 R4**，按[部署合同](../../current/TOKYO_RUNTIME_DEPLOYMENT_CONTRACT.md)执行：

1. D5 全部通过后冻结唯一候选；确认本次包含哪些 API／前端／DB／Kernel 产物和精确身份。
2. 官方认证验证整个允许区间，不只验证 2%；基于候选 commit 产生证书，不复用旧 SHA。
3. 发布行动前重新核验当前源码、机器、PG 与交易所、Owner 权限及真实部署窗口。
4. 只有当前合同要求的空仓、无残单、无未决命令／Incident／预算债务和准备状态全部满足，才进入切换。
5. 官方维护 ENTRY 围栏与停写，包含独立 Owner API；旧新 writer 互斥。冻结历史和完整控制保全基线。
6. 执行精确前向迁移、官方发布与匹配的 API／V2 部署；默认有效 r 保持 2%，保留实际 view 和暂停意图。
7. 通过历史保全与新身份 postflight；仅按真实 Owner 已有授权走官方恢复流程，Owner 主动关闭 ENTRY 时不自动恢复。

无合法窗口则等待既有生命周期，不强平／撤单凑空仓。部署失败按官方恢复／fix-forward 流程，
不重启旧 schema reader、不进行直接 SQL 参数修复、不倒改审计。
源参数不等于预期初装基线时重新评估，不自动覆盖。

## 9. D7：交付口径和后续参数修改

完成交付须分别提供：

- **软件证据**：精确候选认证与正式部署成功。
- **参数证据**：首次 r=2%，总计 6%，方向基线 4%；旧 view 和权限保持；UI／API／PG／Kernel 一致。
- **切换能力证据**：2%↔3% 及并发／重启本地生产形态测试通过；首次投产不为验收改 Owner 配置。
- **实盘证据边界**：自然新命令出现时检查实际版本、发送窗口、接单和 Initial Stop；没有新信号就明确待验证，不下测试单。
- **运维证据**：重启与后续发布不重置有效值；配置错误和 pending 可见且可恢复。

上线时同步现有实验风险契约、Owner 运行模型、解释文档及路线图；当前设计稿不提前替换正式运行合同。
部分 TP1 缺陷状态单列；若未闭合，不能宣称该功能使整条交易生命周期完全健康，也不能把修复偷偷并入参数变更。
