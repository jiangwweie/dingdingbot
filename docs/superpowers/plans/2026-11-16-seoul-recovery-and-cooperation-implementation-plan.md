## 1. 目标与授权

### 1.1 同一成品的两个实施模块

1. **R：优先完成当前生产链路修复**。零仓位残单事件合法处理、正确撤单命名空间、确定性失败有界恢复；正式处理积压事件，核实已平票终态/预算以及仍有仓票的管理能力。
2. **C：完善人工操作后自动续管**。在原策略不变的前提下，手机减仓/止盈/保护/全平/启停有准确授权、唯一执行链、持久化进度和可核实结果。

**Owner于2026-11-17明确要求最终成品一起上线：R、S、C本地可分模块实现和认证，但不先部署仅R修复；最终候选包含故障修复、已批准资源配置、手机Web及完整后台续管，统一完整验收后等待Owner确认部署。** 不把未完成功能、模拟入口或未验证交易所能力作为可用产品发布。

### 1.2 Owner已确认

- 本地编码测试已授权，两个生产代码缺陷要求修复。
- 首尔交易worker共享资源上限**CPUQuota=150%、MemoryMax=1536MiB**已批准；TasksMax128保持。仅首尔，不修改Tokyo默认。API、PG、频率、限流和风险上限不随之提高。
- 首版系统内操作默认继续AUTO；不放宽止损、不加仓、不提高风险。
- 主动减仓可浮盈或浮亏；替代原自动TP1数量退出，保留原目标价供后续BE/Runner转换，不伪造TP成交。
- 避免TP正在成交时并行减仓；若确认期间发生竞态，系统核实并停止新动作，不能让Owner负责不明账务。
- 独立人工计划普通限价、单计划、完整真实成交后续管，取消不擅自恢复旧TP。
- 主屏幕Web原型已认可；长期登录、单可信注册、无TOTP为目标授权合同。

### 1.3 不在本计划

方案A、无固定TP的全策略退出改造、新Regime、半风险档位、局部两次失败暂停与恢复、放宽保护、固定人工结构Stop、较宽Runner、加仓、提高交易风险。MA50是已上线基线，不是本次新增交付。

### 1.4 发布权限

本地实现与测试、资源目标批准不等于所有生产门禁已经满足。正式安装/迁移/恢复按当前Owner发布指令及项目程序执行；真实暂停/Resume不得伪造。不得为了事故恢复跳过活动仓、未知订单或认证门禁；不直接改消费水位、预算、Ticket、授权或删除失败事件。用户未授权本轮测试订单。

## 3. 推进顺序与依赖

```text
R0 独立修复提交 → R1 模块认证与恢复路径 ─┐
S0 首尔专属资源配置 ──────────────────┼→ 最终成品认证 → Owner确认 → 联合安装/重放/验收
S1/S2资源应用与峰值观察安排在联合上线之后
C0 协议门 + 状态规格 → C1 持久化与授权 → C2 操作执行/生命周期
→ C3 其他操作与真实API → C4 手机接入 → C5 全链认证 → C6 联合发布
```

S0可在R1期间准备，但资源提额不替代修bug。R先闭合代码与恢复路径，C随后并入最终成品；生产部署等待完整产品及Owner确认。每个任务默认由当前执行agent负责，不自动建立并行代理；共享Schema/Reducer/Command变更串行整合。

## 4. R工作包：事故修复优先

### R0 — 分离、审查和固定修复候选

- **目标**：可独立审查的事故修复模块，随完整成品联合发布，不包含未完成的手机写功能。
- **范围**：observe_trade_management、reducer cleanup、pg_management_feed、feed/observation worker及对应测试；相关部署/认证资料。
- **任务**：审查零仓只读状态白名单；精准namespace和历史错误命令处理；savepoint失败保全；每版本3次退避与blocked；新runtime对旧epoch按序重放；无未消费事件被重置。
- **验证**：真实162/163离线输入，未成交ENTRY不绕过管理权；有仓正常接管保持；regular/conditional反例；未知命令/撤单/重启；诊断哈希和重试次数持久化。
- **完成**：固定修复diff及精确候选身份；现有用户其他修改保留，新功能不得被误打包。

### R1 — 完整认证与当前现场恢复方案

- **依赖**：R0。
- **任务**：按正式Release流程跑单元/架构/集成/full-chain/static与产品隔离检查；重新读取首尔账号/主机/PG身份、Owner控制、活动仓、残单、命令、事故和水位。
- **关键边界**：之前BTC快照不作当前事实；若活动仓或冻结条件不允许升级，应写出符合现行合同的恢复路径，不自行平仓或在活仓下绕过认证。
- **完成**：精确认证有效且现场安装前条件明确；恢复操作有预览、停止条件与证据路径。

### R2 — 正式恢复及逐对象验收

- **依赖**：R1、有效Owner发布权限和行动时门禁。
- **任务**：正式安装候选；官方worker重放旧epoch162/163。对已生成错误namespace的历史Command，查明真实订单后用正式核实/终态流程处理，不篡改payload或盲重发。
- **完成证据**：
  1. 队列应用水位按序推进，原事件/诊断保留，无重复异常风暴。
  2. BNB/XRP实际flat且残单/未知结果清零，正式终态/结算/预算与标的释放。
  3. BTC独立核实真实仓位与保护，REVIEW依据完整解除或明确保留，不能只因feed ready强清。
  4. 新开仓资格、五服务、API/通知状态以及真实Owner控制分别核实；不把进程alive当交易正常。
- **失败处理**：停新的危险写入，保留venue保护与历史证据，按正式恢复程序前向修复。未完成逐项证据不宣布生产恢复。

## 5. S工作包：已批准的首尔资源余量

### S0 — 首尔专属配置与安装校验

- 交易worker共享slice：CPU100%→150%，MemoryMax1GiB→1536MiB，TasksMax128不变。
- 通过manual产品专属override/profile与安装器管理；保持通用Tokyo slice原值，不主机手改后遗留配置漂移。
- 检查所有父slice与实际cgroup值；服务自身infinity不能替代共享边界核实。
- API保持CPU25%/256MiB，PG保持CPU0.5核/768MiB。无交易风险、限频或事实有效期改变。

### S1/S2 — 应用与观察

- 已批准参数，但应用需与正式维护/认证流程协调；不因本计划直接重启服务。
- 应用后核实实际`cpu.max`、`memory.max`及父级限制；其他服务配置保持。
- 覆盖至少一个整点与4h边界观察CPU节流增量、内存峰值/OOM、PG连接/延迟、feed lag、行情刷新和Lifecycle耗时。
- 两核主机上各服务CPU配额总和可超过物理核数，配额不是预留；记录竞争与P95/P99。若无瓶颈，提额仅代表突发余量，不承诺单笔更快。

## 6. C工作包：人工操作后自动续管

### C0 — 协议证据与统一状态规格

- **输入**：[执行V1](../specs/2026-11-16-owner-cooperative-execution-v1.md)、[减仓决定](../specs/2026-11-16-owner-reduction-replaces-tp1-decision.md)、[可行性核验](2026-11-16-cooperative-control-feasibility-and-task-cards.md)。
- **任务**：完成Hedge平仓方向、Stop与market close竞态、Close-All候选保护、TP取消/部分成交/超时证据；确定已发Command和实际减量的精确身份绑定。
- **禁止**：正常Stop被当作外部Owner接管；直接将状态改MANUAL后遗弃在途命令；把合成回放冒充真实交易所保证。
- **完成**：每个动作有明确前置、允许效果、未知路径及停止条件；无法证明的真实能力保持关闭。

### C1 — operation、事件与Schema

- **范围**：domain/application/PG repositories/models、单条forward migration、测试；不建第二账本/执行链。
- **任务**：操作预览/幂等/版本、追加事件和当前投影；实际减量独立事实；原TP退休原因、目标价格条件、保护确认阶段；预算/Review读取真实成交。
- **验证**：重复/乱序/部分成交、事务回滚、重启、相同key不同body、过时预览、金额Decimal与数量守恒。
- **完成**：不依赖JSON文件或内存会话的恢复；无干预AUTO票行为不变，MANUAL不可暗中回AUTO。

### C2 — 减仓、保护与续管接入

- 预览→精确撤原TP→核实期间成交→市价减仓→核实实际余量→确认保护→等待原目标价→原BE/Runner。
- 原TP已在成交/未知时不新发减仓；取消后零成交拒绝按合法原计划恢复，否则保留Stop并明确受阻；部分成功不补发剩余。
- 真实减量后才形成价格条件分支；原失败/时间退出优先；价格回穿BE按原明确退出处理，不放宽、不追损。
- 每票串行，其他票正常运行；所有venue写先耐久Command再dispatch；权限与事实在发送前重新核验。
- **完成**：真实协议形状与本地PG全链覆盖，包括Stop先平/后平、外部接管、设备撤销、残单清理；仍未通过的live门保持关闭。

### C3 — 其他人工操作与授权API

- 收紧保护只提高已确认约束；人工计划单一替换/取消；全平、全局/策略启停沿原权限与语义。
- 单可信注册、独立绑定/撤销、长期持久会话、无TOTP真实授权；旧历史TOTP不篡改，不用字符串伪造认证强度。
- API生成预览/意图并查询结果，不直连交易所；用途白名单不扩到资金划转、加仓或风险上限。
- **完成**：权限/CSRF/nonce或最终选定设备证明、撤销、恢复、重复请求、会话重启、Owner手动暂停优先全部测试。

### C4 — 手机原型接真实后台

- 保留已认可的持仓/委托/主控及单策略开关；只读取必要操作事实。
- UI能区分受理、处理中、部分执行、拒绝、待核实和已确认生效；根据后端capability禁用未支持动作。
- 主屏Web安装/网络恢复/关闭页面后查询；交易API不缓存、不离线排队重发。
- 关键通知复用outbox，失败不伪装已送达，不将通知故障变交易指令。
- **完成**：真机流程覆盖，无说明文字堆砌；原型模拟与真实入口清楚分离。

### C5/C6 — 认证、联合发布及验收

- 核心先红绿，针对性检查后完整Release；原TP/BE/Runner、人工接管、事故修复均回归。
- 停新入场、flat、停writer、前向迁移、历史保全、精确身份认证和官方promoter；设备绑定与真实Owner恢复独立完成。
- 发布手机不自动激活新交易策略。需要自然业务证据的项目留待自然发生，不下未授权测试单凑验收。
- **完成**：按动作分别证明数量/保护/收尾/账务/通知；未覆盖的自然场景明确标注，不能用静态原型或纯决策测试宣称全部完成。

## 7. 关键验收底线

| 边界 | 必须证明 |
|---|---|
| 队列 | 不丢、不跳过；确定性失败有持久原因和有界重试 |
| 管理权 | flat不错误接管；外部有效干预不被当系统自身；MANUAL不可自动恢复 |
| 订单 | regular/conditional精确身份；未知不重发；零仓残单不提前释放 |
| 减仓 | 人工减量不是TP成交；不二次扣数量、不创造反向暴露/第二ENTRY |
| 保护 | 不裸撤唯一保护、不放松Owner或系统已确认约束；仅已核实结果显示生效 |
| 授权 | 真Owner、明确用途、可撤销；长期登录不等于永久不可撤销权限 |
| 策略 | 无人工时原策略行为不变；无MA50/Regime/风险改造混入 |
| 发布 | 精确候选、历史保全、现场行动门禁，不跨产品、不带未完成写入口 |

## 8. 状态管理与沟通

每阶段只报告事实：完成文件/行为、实际测试、未完成项、是否具备现场启用证据。开始后续工作不必重新询问已确认业务；出现扩张风险、改变操作意图、交易所不支持目标行为等实质分歧再向Owner提出具体选择。

本次资源参数已确认，现阶段无须重新讨论该数值。生产故障恢复优先；现场仍存在活动仓或未知结果时按真实事实选择正式恢复路径，不推定用户已暂停/平仓。
