## 1. 建议决策

**优先采用方案 A：首尔 Entry 定向采用 Tokyo 的 10 秒读取超时、30 秒行动事实有效期，同时补齐真实读取时序认证、结构化错误诊断；最终发送授权窗口仍为 5 秒。**

这是一项需要本次复核明确接受的**事实新鲜度边界调整**：首尔允许的事实年龄从 5 秒增加到最多 30 秒，不能称为“风险边界完全没有变化”。资金、仓位容量、杠杆、止损风险、策略选择及人工接管规则均不随之改变。

**如果 Owner 要求事实有效期必须保持 5 秒，则采用方案 B，重新设计读取调度并重新认证；不以关闭限速或改写时间戳实现。**

本方案不是安装或开仓授权。后续执行以复核结果、正式发布流程及行动时门禁为准。

## 3. 根因与三个时间概念

### 3.1 已证实的失败链

```text
自然 StrategySignal
→ Entry 并行请求 admission snapshot 与 instrument rules
→ 同一个 CCXT 实例的 FIFO 加权限速队列
→ 两个全账户挂单查询各 cost40，持仓模式 cost30
→ 后续规则/账户/仓位查询排队约 5.65—5.75 秒
→ 首尔外层 5 秒超时
→ admission rejected / observation_unavailable
→ 无 CapacityClaim、Ticket、Exchange Command
```

实际 HTTP 请求成功；网络耗时远小于排队时间。探针保留原 CCXT 限速，只将独立诊断协程等待上限设为 20 秒以观察完成结果，未改变生产进程。GET-only guard 拒绝所有非 GET 请求。

调用路径：`entry_worker.py:214` → `venue_adapter.py:263/438/495` → 已部署 CCXT `Exchange.fetch2` → `Throttler` → HTTPS。两笔全账户订单查询是账户风险审查的一部分，不能擅自缩成目标标的查询来省权重。

### 3.2 必须分别管理的时间边界

| 边界 | 起点与含义 | 推荐方案 A |
| --- | --- | --- |
| 读取超时 | 一轮采集开始，包含排队、HTTP、解析；每轮独立受限 | 10 秒 |
| 行动事实有效期 | 当前模型以采集请求开始时间记账；超过即拒绝 | 30 秒；从真实开始计时，不在完成后重置 |
| 最终发送授权 | 最后一次实时核验及短事务授权后开始 | 最多 5 秒；取全部相关截止时间最小值 |

Ticket 创建前采集一次，ENTRY 真正发送前**重新采集并核验一次**。不复用上一轮事实代替发送前读取。发送签名仍绑定已持久化授权时间，Binance `recvWindow` 上限保持 5 秒。

**30 秒不是无条件允许发送 30 秒，也不是延长信号、租约或订单期限。** 它确实允许较旧事实，风险为采样后账户/行情变化；通过逐单重新采样、发送前核验、真实期限交集和既有成交后风控约束，而不是声称变化不存在。

### 3.3 为什么前次认证未暴露

只读数据库认证证明结构、身份和门禁状态；维护探针有自己的多标的采集窗口。它们没有等价执行 Entry 生产参数下的两轮采集时序，因此 `entry_recovery_ready=true` 不等于真实订单读取链路已通过。

本次必须补齐“生产工厂 + 部署依赖 + 生效参数 + 实际加权限速”的认证覆盖，不能以延长维护探针窗口冒充修复。

| 方案 | 改动 | 收益 | 代价 / 风险 | 结论 |

| **A：Entry 定向采用 10秒 / 30秒** | 受版本管理的角色配置、安装及认证；保留现有读取和限速 | Tokyo 同路径有直接运行证据，改动范围小 | 明确扩大首尔允许的事实年龄，需要 Owner 接受 | **推荐本轮** |
| B：保留 5秒事实期，重构读取预算与调度 | 采样前完成预算等待，整组读取控制突发与总权重，精确记录各事实时间 | 保持更紧的数据年龄上限 | 跨限速、并发、取消和多 Worker 总权重的设计与验收较重；目前未验证可达标 | Owner 坚持 5秒时选择；未达标继续拒绝 |
| C：仅把超时改为 10秒，事实期仍为 5秒 | 单参数修改 | 可等到 HTTP 返回 | 返回时事实已过期，CapacityClaim/dispatch 仍拒绝 | 排除 |

同时排除：关闭 CCXT 限速；为每个请求新建客户端绕过配额；只查目标标的而忽略其他账户订单；缓存旧事实授信；把采样时间改写成完成时间；自动复活已拒绝信号；直接生成测试订单。

### 4.1 A 的具体配置边界

- 只针对首尔 **Entry 角色**调整 10秒/30000ms，使其命令行、生产适配器 HTTP timeout、准入与 dispatch 两次采集读取同一组生效参数。
- 现有 `timeout_seconds` 是 Entry 角色共用超时，也用于该角色的交易所命令等待。因此方案 A 会把 Entry 请求/命令结果的最长等待从5秒调到10秒；**它不把请求签名、最终发送授权或 Binance recvWindow 扩到10秒**。若发送后结果未知，仍进入现有 unknown/reconciliation 路径，不因等待超时重新发单。这一附带影响必须纳入测试和复核，不能称为“只影响 GET 的配置”。
- 使用正式安装流程管理 Entry 专用环境配置和 systemd 加载顺序；例如在公共环境之后加载只含两项非秘密参数的 Entry 环境文件。最终以 `/proc` 进程参数和环境回读验收，不仅查看磁盘文件。
- 不直接改全 Worker 共用环境而顺带改变 Observation、Lifecycle、Reconciliation。新安装与升级都必须生成相同结果，防止下次发布回到 5秒/5秒。
- 配置来源和准确值纳入发布清单与当前门禁；缺失或未认证组合应明确阻断，不静默采用 CLI 默认值。
- 首轮不新增数据库表、不迁移 schema、不改策略/资金策略，也不更换 CCXT 版本。

## 5. 其他问题的处理边界

### 5.1 退休 SOR 循环

首尔 Observation 无条件启动旧 SOR daily Selection/Materialization 循环，缺少控制记录时每轮报错。删除退休策略的新选币与新 Universe 物化调度；保留历史查询、Registry 和在途事实的只读解释能力。SOR-1H 是独立活跃策略，必须继续运行。

不得把“Owner 暂停”一概当作可删除循环：CPM/MI 等可恢复策略仍需合法 drain/recovery 维护。只有**永久退休 SOR**适用退役规则。公共修复移植 Tokyo 前，要证明不依赖该循环处理历史未决工作；不删除其历史数据库记录。

### 5.2 总览新鲜度

两产品 `_overview_freshness` 都把占用账本 `updated_at_ms` 作为必须新鲜的运行证据。账本按交易占用/释放更新，空仓或长时间稳定持仓都可能无变化。Tokyo 有真实受保护持仓仍显示 unavailable，证明问题不限于空账户。

拟采用以下定义：

1. **资金占用账本**校验存在性、账户身份、版本和与 Ticket/预算的一致性；不以无变更时间认定采集断流。
2. **账户同步新鲜度**使用精确账户的 `position-audit` 事实及状态，不能用任意最新通知、BNB 或其他 monitor 代替。
3. 阈值依据真实审计 cadence。当前 cadence 为 60 秒，拟采用不超过 120 秒为 fresh、120—300 秒 stale、超过 300 秒 unavailable；这是展示阈值，不是开仓事实 TTL。边界值及审计失败立即降级需要测试。
4. 明确区分“账户最近同步”与“全系统正常”。单个 position-audit 不能证明所有 Worker、退出挂单或当前信号链路健康；开放 Incident、矛盾、Entry 读取失败应分别展示。
5. 不在 GET API 中修复投影，不为保持绿色而周期性改写占用账本，不让该展示结论成为交易授权。

### 5.3 错误可观察性与通知

- 在同一事实读取边界记录阶段、超时类型、限速等待/HTTP/总耗时、准确 Signal/Command 身份；禁止输出签名 URL、API key、DSN 或 webhook。
- Entry 读取失败写入明确的当前健康投影或现有准入事实解释，使“进程运行中”与“开仓读取受阻”同时可见。不能由通知通道健康覆盖交易异常。
- 相同原因的重复日志聚合/限频，状态变化立即记录；真实 ValueError、未知归属与失败门禁不能统一当 idle 吞掉。
- 飞书真实到达仍依赖自然业务事件和平台回执；不发送额外测试消息，不把 outbox 为空认定为通知链路已验收。
- BNB 由 Owner 自行研究开启；不增加余额、不切换设置、不把该提醒纳入开仓硬阻塞。

## 7. 验证标准

### 7.1 有意义的 RED / GREEN

| 场景 | 旧行为 / RED | 新行为 / GREEN |
| --- | --- | --- |
| 相同 CCXT 权重、已加载市场、账户无挂单 | 5秒超时；不是瞬时 fake | 10秒内完整返回，真实开始时间下事实仍有效 |
| 入场前与发送前各一次读取 | 只验证第一次会漏掉发送失败 | 两次均真实重采样，授权提交后发送窗口不超过5秒 |
| 冷启动、连续候选、队列残余、超时取消后下一轮 | 单次暖机样本无法覆盖 | 无任务泄漏或取消债务积压；无法满足时明确拒绝 |
| 读取超过10秒、事实超过30秒 | 原门禁应拒绝，修改不得破坏 | 不产生新写；不能重写事实时间绕过 |
| Policy/方向/币池/管理权在 I/O 中改变 | 旧权限可能被使用 | I/O 后按当前状态重验；MANUAL 永不自动写 |
| 全账户其他标的订单/相反方向占用 | 目标标的查询会漏检 | 保留完整全账户审查，继续拒绝不允许的占用 |
| 占用账本长期不变但审计更新 | 总览 unavailable | 账户同步可 fresh，账本一致性仍须通过 |
| 审计过期或失败、其他 monitor 刷新 | 可能显示假健康 | 账户同步降级，不被通知或BNB刷新掩盖 |
| SOR 退休但 SOR-1H 正常启用 | 旧循环反复 blocked | 停止退休调度，保留小时策略及历史解释 |

先跑受影响单元/集成测试，再对冻结候选执行仓库要求的完整发布认证。使用本工作区 `.venv`、`scripts/local/manual_pytest.sh` 和独立手动产品 PostgreSQL。

### 7.2 发布前真实只读证据

- 使用已安装生产工厂、相同 CCXT 和**拟发布的 Entry 进程参数**，覆盖当前 Owner-enabled Active Universe 每个成员；基于准确账户执行完整只读采集。
- 做冷启动、连续两轮准入/发送前读取和限速剩余队列场景。记录实际样本最大值及成功/失败数，不用三次采样声称 P99。
- 提案验收目标：每轮采集 <10秒，最终授权阶段仍有有效期限；若经常接近截止，不靠继续扩 TTL 通过，应退回优化设计。
- 同时核对所有账户订单、持仓模式及现有 AUTO/MANUAL 权限；探针明确禁止所有交易所非 GET 请求。
- “只读能够采集”与“自然订单被接受并保护”分开验收。后者只能由正式运行时处理新自然信号证明。

## 8. 发布、失败与恢复

1. **复核前**：仅保存方案与只读证据，停止在待审状态。
