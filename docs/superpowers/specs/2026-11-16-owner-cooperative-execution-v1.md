# 人工操作后自动续管：执行设计V1

日期：2026-11-16。**当前操作语义的统一入口；供实施前审阅，未授权编码、部署或激活。** 本稿取代旧详细设计中“减仓保持/等比缩减原TP”等冲突分支；授权/PWA/API基础继续引用[手机详细设计](2026-11-16-mobile-owner-control-detailed-design.md)。

## 1. 已确认范围

现有入场、MA50、风险上限及无人干预时的TP/BE/Runner保持不变。手机系统内调整默认继续AUTO；首版只收紧保护，不做放宽、固定人工结构Stop或较宽跟踪计划。外部币安App介入仍走现有MANUAL/REVIEW合同，不自动接回。

主动减仓可在浮盈/浮亏时发生，真实成交替代原自动TP1的数量退出。取消原自动TP1订单，但保留其目标价格作为余仓管理转换条件；达到后申请原费用感知BE，保护确认后Runner。余仓保本不追回已实现亏损，不等于整票保本。

Owner不要求TP触发/成交时与人工减仓并行。首版在TP正在触发、已有部分成交未闭环、未知订单或已有操作时拒绝新增减仓，先核实。系统仍负责确认前后发生变化的竞态，不把Owner操作习惯作为安全证明。

## 2. 操作允许矩阵

| 当前事实 | 主动减仓 | 后续 |
|---|---|---|
| AUTO、原TP未触发/无成交、保护及余量准确 | 允许预览并确认 | 撤原TP、核实、减仓、余量保护、价格条件管理 |
| 已确认进入Runner、无在途动作 | 允许 | 核实减量、更新保护、继续Runner，不重置阶段 |
| TP触发附近或正在成交、部分成交尚未完成阶段处理 | 暂不接受 | 刷新原生命周期，不能追溯伪造TP完成 |
| REVIEW_REQUIRED、未知执行结果、在途改单/退出 | 拒绝新操作 | 核实后重新预览 |
| MANUAL | 无AUTO续管入口 | 保持现有接管规则 |
| 另有独立人工计划且与本次减仓冲突 | 不并行执行 | 提示先处理原计划，再重新预览 |

独立人工止盈功能继续保留，但本次主动减仓分支不静默取消/改量任何独立人工计划。首版可用性保守串行；若Owner今后需要两者联动，另行设计。

## 3. 正常执行与不可逆边界

1. 预览冻结Ticket、管理版本、实际余量、原TP订单与累计成交、已确认Stop、目标减量、价格条件。预览30秒，数量/订单事实变化失效；重复确认同幂等键返回原操作。
2. 受理后锁定该票新派发；后台原必要保护保持。当前价格已越原TP目标或有任何TP新成交则不进入减仓流程，先完成原生命周期事实核实。
3. 创建精确取消原自动TP的Command。等待取消终态并查询期间成交；取消未知不发减仓。期间任何新成交/余量变化使原预览失效，不按旧Q发送。
4. 已确认无期间成交且余量未变后，在发送前再次核对价格、方向、保护、授权及管理权；满足才发送唯一市价减仓Command。取消TP不等于实际减仓，不生成转换完成事件。
5. 实际减仓成交和订单终态核实后，按真实余量更新保护。保留原TP价格，进入`owner_reduced_wait_price`；不重新挂原TP，不伪造TakeProfitFilled。
6. 价格条件满足后生成独立`OwnerReductionPriceConditionSatisfied`，调用原BE计算/保护过程；保护确认后Runner。价格已经穿越拟安装BE时沿原明确退出分支处理，不放松保护、不等待Owner盯盘。
7. 全部归零则不进入BE/Runner，清理残单、结算。部分减仓只记录实际量，未成交余量不自动补发。

数据库事务持久化operation/授权/Command与阶段，网络I/O在事务外；每次推进核对精确revision；原始成交和价格证据追加保存。

## 4. 价格条件证据

使用与原TP价格语义一致的合约成交价；做多当前有效价≥目标，做空≤目标。起算点是**实际减仓已核实**，更早的K线高低不能追溯触发。

复用已认证的行情新鲜度约束，记录instrument、side、source、observed_at、价和计划revision。一次条件满足持久化后不因后续回穿取消事实，但BE能否安装按行动时当前价格与原退出规则处理。

不依靠历史触价补造收益，也不要求原本已取消的TP再成交。断线期间是否触价未知，恢复后按当前有效价格判断；漏掉瞬时触价是低频采样的明确边界，既有Stop仍保护。此为工程初始规则，不引入新的盈利门槛。

## 5. 失败与竞态恢复

| 已发生事实 | 处理 |
|---|---|
| 尚未撤原TP，预览过时/授权撤销 | 不发送；原计划不变 |
| 原TP取消失败或结果未知 | 不发送减仓，精确查询；不重发未知命令 |
| 撤TP期间TP已成交 | 记录真实成交，交原生命周期处理；人工减仓取消/需重确认 |
| 原TP已取消、减仓未发送或明确零成交拒绝 | 未形成人工减量计划。若原价/原量仍合法则经耐久命令恢复原TP；否则维持Stop，显示计划恢复受阻，需核实或Owner处理；不越价偷偷市价平仓 |
| 市价减仓结果未知 | 不恢复可能导致过量退出的TP、不重发减仓；保留/核实Stop，查询成交和余量 |
| 市价减仓已部分成交且终态 | 实际减量成立，按实际余仓续管；标部分执行，不自动补发剩余；原TP数量退出不恢复 |
| 取消TP后、减仓发送后目标价被市场达到 | 以实际减量和当时行情事实按§4处理；无法完全消除交易所与本系统竞态 |
| Stop与减仓交错成交 | 仅按确认的真实余量继续，归零收尾；不得生成反向仓或额外ENTRY |
| 外部App介入 | 停止新增操作写入，原MANUAL/REVIEW规则优先；已发生效果继续核算 |
| 重启/客户端关闭 | 从持久化阶段查询恢复；不重新执行起始命令，不依赖手机在线 |

恢复原TP属于恢复尚未成功改变的原授权计划，不是自动恢复Owner明确取消的人工计划。两种取消目的必须在事件中区分。

## 6. 人工止盈和保护

独立人工TP替换自动TP的已确认规则维持：最多一个活动获利计划；新目标完整真实成交后沿原BE/Runner；取消人工计划不恢复旧TP，不伪造完成。若替换前有部分成交，冻结已成数量与新待成交目标分别记账。

收紧保护先预览差异，申请价与已生效价分别显示；系统之后可以更紧，不得放松。失败不假报生效。首版不做放宽。

## 7. 实施前技术验证与交付标准

**业务选择已足以继续技术设计，不再要求Owner回答常规竞态处理。** 尚需实现前核实：

- Binance USD-M Hedge准确close侧、零仓/超量请求行为，旧Stop在减仓后与后续改单是否保持真实保护；不能靠不存在的reduceOnly参数作保证。
- Stop替换与撤TP的原始HTTP/WS/CCXT协议回放；部分成交、已取消仍有延迟成交、超时/重启案例。
- 当前Aggregate/Reducer/maintenance新增价格条件分支，保持无干预原策略不变；历史TP事件与新减仓事实不能混用。
- 认证用途、可信设备撤销、命令发送门及操作恢复保持单一授权链。

上述是技术证据任务，不是已完成安全认证。若协议不支持持续保护的减仓方式，必须停止该功能实现并说明真实限制，不把问题包装成Owner选择。

文档验收：唯一分支、每个副作用有恢复路径、引用有效。实施验收：红绿核心行为测试、原协议回放、原策略回归、故障恢复与精确发布认证。代码和上线仍需后续授权。
