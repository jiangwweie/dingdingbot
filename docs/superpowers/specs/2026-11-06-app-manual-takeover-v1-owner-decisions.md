## 1. 目标与最终方案

Owner 的主要需求是**难以发现交易机会，希望程序发现机会并自动下单**。
Owner 可以在交易所 App 提前止损、部分或全部减仓、修改止盈止损，
不必等待系统的 TP1 或 Runner 条件。

最终方案是：**默认全自动，人工干预后整笔永久转人工管理。**

1. 无人工干预时，沿用现有入场、初始止损、TP1、Runner 和其他自动退出规则。
2. Owner 在 App 对该笔交易作出交易所确认的操作，即视为接管，**不要求触发成交**。
3. 即使只干预一部分，也接管整笔剩余仓位及相关退出订单。
4. 接管后直到该笔交易结束都不恢复自动管理；改回原价格、重启或升级均不改变管理权。
5. 既有 TP1、止损及其他退出挂单继续有效，由 Owner 决定保留、修改、撤销。
6. 系统继续只读同步、记账和核算账户占用，不再主动处置这笔交易。
7. 后续独立的新交易默认仍为自动管理，不继承上一笔的人工接管状态。

**早期讨论的“取消 TP1/Runner”“初始止损完成后自动交付人工”已经被最终决定取代，
不得作为本版本需求。** 本次也不引入新的左侧信号策略或 SOL 专题能力。

## 2. 两条产品线与部署隔离

| 边界 | Tokyo 全自动产品线 | 新服务器人工接管产品线 |
| --- | --- | --- |
| 分支 | 现有 `dev` 集成和发布流程 | `codex/app-manual-takeover-v1`，从同步后的 `dev` 分出 |
| 默认行为 | 现有完整自动生命周期 | 同样完整自动生命周期 |
| 外部人工操作 | 保留现有规则，不通过本任务改动 | 按本记录识别并接管 |
| 交易资产与权限 | 现有账户、凭据与风险预算 | 独立交易子账户、凭据与风险预算 |
| 数据与账本 | 现有数据库与交易历史 | 独立数据库与账本 |
| 发布 | 独立认证、部署 | 独立认证、部署，不联动 Tokyo |

新服务器是独立实验环境，不是 Tokyo 热备或活动持仓迁移目标。
可以复用代码和经过确认的配置；**不得复制活动 Ticket、持仓、当前订单、授权事件、
运行身份或账本来制造新环境已授权/已持仓的事实**。初始化应经过正式流程。

两个环境分别运行完整 Kernel，不能让两套程序同时解释或写入同一交易账户的仓位。
独立多空账户能力仍然保留；新产品的同标的双向禁入属于策略准入规则，
不意味着擅自把交易所账户改成单向模式。

### 2.1 共同迭代原则

- 通用工程修复按独立改动评估后移植到两边，各自验证。
- 人工接管专属语义只进入新产品线，不整分支反向合并进 `dev`。
- 策略信号和参数调整单独决定是否同步，代码同步不自动扩大策略范围。
- 两个分支分别维护适用的迁移链、运行身份和精确提交证书；证书不可跨分支/SHA复用。
- 不让任一环境读取另一环境的当前数据库作为运行 authority，不建立双写或旧表回退。
- 新产品线未来的生产状态记录与部署目标须明确区分；本记录不新增第二份 Tokyo 状态快照。

## 3. 已确认的交易边界

| 事项 | Owner 决定 |
| --- | --- |
| 首次入场 | 必须由程序发现机会并发出订单，不逐笔等待人工确认 |
| 运行时段 | 全天自动运行，和现有方式相同；初始有止损是 Owner 接受该入场的前提 |
| TP1 与 Runner | 保留；未干预时与原自动逻辑一致 |
| 人工加仓 | 首版不支持，Owner 不增加仓位 |
| 人工重新开仓、反手 | 不支持；不能算原系统交易的继续管理 |
| 人工操作范围 | 部分/全部减仓，新增、修改、撤销相关退出订单 |
| 止损 | Owner 计划修改而非撤掉；系统不自动纠正人工修改 |
| 止损缺失的意外情况 | 如实识别、告警并处理新增开仓资格，不声称仍完整保护，不擅自重挂 |
| 强制处置人工仓 | 不需要；交付后的程序不因风险变化自动平掉人工仓 |
| 残留订单 | Owner 撤销，包括程序原来挂出的 TP1 和止损 |
| 自动补仓 | 禁止，不补回 Owner 减掉的数量 |
| 重复机会 | 不允许复用同一个 Signal/Exposure Episode 再次开仓 |
| 额外冷却 | 不增加统一时间冷却，未来新机会遵循现有重新触发条件 |
| 同标的双向持仓 | **禁止同时持有多空仓位**，准入需核对相反方向的实际占用 |
| 资金与风险配置 | 沿用 Owner 确认的现有配置，不自行扩大或重置；实施时明确配置快照 |
| 保本后释放额度 | 不将名义保本当作无风险，不据此无限增加仓位 |
| 每日亏损熔断 | **不新增**；Owner 自行决定关闭全局 ENTRY |
| 数据缺失或风险不明 | 限制新增自动开仓，继续核实，不盲目改动人工仓 |
| 通知 | 初始保护/交付准备确认、人工接管确认和关键风险变化通知；不重复刷屏 |
| 人工收益归因与操作建议 | 首版不新增这类分析或指导功能；必要账务与事实记录保留 |
| SOL 专题 | 不在本次讨论和改造范围内，不据此自动变更币池 |

“沿用现有配置”不是把历史文档中的默认值直接写入新账户。
后续实施应读取并确认当时适用的 Owner 配置，记录来源和版本，并走新环境的正式授权。
服务器地址、账户标识及部署凭据属于后续落地信息，不是未决交易规则。

## 4. 干预与接管识别

**Owner 的定义：只要我动了，不管是否触发成交，就算接管。**
程序以交易所可核实的外部操作为依据，不能观察 App 中未提交的编辑。

| 可观察事实 | 处理语义 |
| --- | --- |
| 外部减仓或全部平仓成交 | 接管整笔交易；全部平仓继续只读完成收尾 |
| 外部新增止盈、止损、减仓挂单，尚未成交 | 立即按接管处理，不等成交 |
| 原有订单价格、数量、触发条件等被外部修改 | 接管，订单编号不变也须能识别 |
| 外部撤销该笔退出订单 | 接管，不能自动补回 |
| 修改/下单被交易所拒绝，未发生其他实际变化 | 不凭失败请求认定已接管 |
| 原程序 TP1、止损自然成交 | 不算人工干预，仍执行自动生命周期 |
| 程序自己的改单、换止损、撤旧止损 | 不算人工干预，必须与本系统命令记录核对 |
| 订单暂时查不到、历史缺失或变化无法解释 | 归属待确认；暂停该笔新的自动处置并告警，不能直接认定人工接管 |

识别目标是“本系统之外对这笔交易作出的有效操作”，不虚构交易所未提供的 App
操作者身份。不得把交易所正常成交、自动取消或故障一概归因为 Owner。
新增人工订单应按账户、标的、方向及退出语义关联，不能只依赖原始订单 ID。

## 5. 接管后的权限

### 5.1 禁止的程序动作

- 新建、修改、撤销该笔交易的止盈、止损或退出订单。
- 自动保本、Runner 追踪、时间退出、结构退出及风险触发的自动平仓。
- 自动补回仓位、恢复原止损、重新挂回 Owner 撤掉的订单。
- 因重启、升级、价格改回原值或原 TP1 成交而恢复自动管理。

**原 TP1 仍可在交易所成交，但成交后程序也不再给这笔人工仓自动移动保本止损。**
剩余数量和保护是否匹配由 Owner 管理；程序展示真实状态，不覆盖 Owner 操作。

### 5.2 继续承担的只读与账务职责

- 读取实际持仓、未成交订单和成交记录，区分订单变化与真实成交。
- 同步部分减仓、剩余数量、已实现结果、手续费、资金费和实际保护覆盖。
- 保留初始入场/止损/风险事实，当前状态另行更新，不重写原始 Ticket。
- 继续核算人工仓对持仓数、资金、保证金和风险额度的占用。
- 提示保护缺失、风险不可计算及残留订单等关键变化。
- 仓位归零后只读确认相关订单终态、结算并释放可证明已释放的占用。

不新增人工操作绩效归因、盈利指导或额外分析产品，不等于删除基础对账和必要账务。

## 6. 入场安全与风险准入

1. 人工接管前仍执行正式开仓路径，包括成交核实、初始止损和成交后风险检查。
2. 正常操作约定为 Owner 等待初始止损成功确认后再干预。
3. 若提前操作，不能宣称已完成安全交付，应先核实真实成交和保护，作为交付异常处理；
   其技术处理由实现方案定义，不凭空增加“所有人工操作前必须在控制台暂停”的流程。
4. 开仓结果未知、部分成交和初始保护失败的既有安全处理，在交付前仍须保留。
5. 人工仓风险超限或无法核算时，限制该新账户新增自动开仓，不擅自处置人工仓。
   其他仍属自动模式的旧仓继续按原规则管理。
6. 持仓减少不自动等于按比例释放所有风险；还须考虑剩余保护、保证金和未成交订单。
7. 人工全平但残留退出订单未核实清楚时，不允许同一标的同方向重新进入；
   Owner 清理并核实后，才可处理符合重新触发条件的新机会。
8. 人工减仓后程序不补仓，人工提前止损后不重复消费原信号。
9. 首版禁加仓是约定及监测边界，程序无法阻止 Owner 在交易所 App 超范围操作。
   若出现实际增仓、反手或新开仓，应标识范围外变化，暂停受影响的新准入并核实，
   不能把它悄悄并入旧 Ticket，也不能盲目平掉。

## 7. 本次明确排除与实施边界

- Owner 明确要求**本轮不讨论人机并发动作**。不把“先在控制台暂停再去 App 操作”
  增加为强制产品流程，也不据此新增一轮业务确认。
- 不承诺程序可以观察 App 点击瞬间或撤回已发送的交易所请求。检测延迟、幂等性、
  已发送请求事实核实及重启一致性属于后续实现验证，不能以文档替代证据。
- 不开发人工加仓、反手、人工自行开仓、人工管理后的自动交回。
- 不取消未干预交易的 TP1/Runner，不为新产品改变 Tokyo 的运行行为。
- 不新增每日亏损熔断、自动盈利建议、人工收益归因或 SOL 轮动规则。
- 不变更机会算法来配合退出方式，不自动扩大策略或资金范围。
- 不在本轮实现交易代码、迁移数据库、购买服务器、配置凭据或部署。

## 8. 后续工程改造与验收方向

以下为由已确认规则推导的工程工作，**不是已经完成的功能**。

| 边界 | 必须实现或验证的结果 |
| --- | --- |
| 管理权 | 每笔自动/待确认/人工状态可持久化；人工接管不回退 |
| 外部变化识别 | 未成交的人工订单和同 ID 修改也能识别；自身操作与自然成交不误判 |
| 命令权限 | 人工仓不会继续被自动 TP、Runner、退出、补单或清理路径处置 |
| 对账 | 人工部分成交、减仓、全平、撤改订单属于可解释的正常事实 |
| 风险占用 | 人工仓仍占用额度；风险未知时新增开仓受限；禁止同标的双向重叠 |
| 原自动路径 | 完全不干预时仍走现有 TP1、Runner 和终态收尾 |
| 恢复 | 重启后保留接管状态并补齐事实，不恢复自动托管 |
| 通知 | 明确通知整笔已接管，并列出剩余仓位与仍有效的退出挂单 |
| 运行隔离 | 两台服务器、账户、数据库、运行身份和发布证据互不混用 |

实现继续使用现有 Kernel 的事实、Ticket、事件和 durable Exchange Command 边界，
不另造第二套绕过风险和对账的交易链。管理权、数据库及发布等级须在实施设计中评估；
正式发布按受影响的最高等级认证，不能只用局部测试宣称可投产。
本记录确认业务规则；实际实施与验收进度见配套计划，不由本决策表推断完成。
