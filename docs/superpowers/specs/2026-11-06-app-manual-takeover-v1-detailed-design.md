## 1. 目标、非目标与证据等级

**默认沿用完整自动交易；Owner 在交易所 App 对某笔交易作出有效干预后，
整笔交易永久转人工管理，系统停止主动管理它的退出，但继续读取事实和计算账户占用。**

### 1.1 已确认的业务规则

1. 系统发现机会、首次下单，全天运行；未干预时保留初始止损、TP1、Runner、时间及结构退出。
2. 外部新增、修改、撤销相关退出订单即触发接管，**不等成交**；外部减仓成交同样触发。
3. 接管范围是整笔剩余仓位；部分干预、改回原值、重启、升级均不能撤销接管。
4. 接管时现存 TP1、止损和其他退出订单原样保留，Owner 接管并清理。
5. 接管后不补仓、不自动恢复保护、不移动 Runner、不自动平仓或撤残留订单。
6. 首版禁止人工加仓、自行重开、反手；新账户禁止同标的多空同时持仓。
7. 不重复消费同一次机会，不增加统一冷却时间；新独立机会默认自动管理。
8. 独立服务器、子账户、凭据、数据库及预算；Tokyo 与其产品分支不改变。
9. 沿用 Owner 确认的现有风险配置；不新增日亏损熔断，Owner 自行关闭 ENTRY。
10. 不新增操作建议或人工绩效归因；必要账务、风险同步、状态通知保留。
11. 本轮不展开人机并发操作场景，不增加操作前必须在控制台暂停的产品流程。
12. SOL 专题、新信号策略、加仓功能不在范围内。

### 1.2 本文技术选择的地位

管理权状态、事件名称、表结构、风险占用算法和采样预算是**技术设计提案**，
不是 Owner 已批准的参数扩张，也不是生产事实。实现必须通过测试和交易所能力核实。
未核实的接口、事件覆盖和检测时延不得宣称可用。

本轮没有刷新生产事实，所有现状陈述只来自当前分支代码；
Tokyo 生产状态仍由[主路线图](../../current/MAIN_CONTROL_ROADMAP.md)与行动时事实共同核验。

## 3. 产品线与唯一权威

### 3.1 独立部署

| 项目 | 全自动线 | 人工接管线 |
| --- | --- | --- |
| 集成 | 原 `dev` 及现有发布流程 | 本分支与未来明确的本产品集成流程 |
| 账户/数据库 | Tokyo 当前环境 | 新独立环境，不共享运行表或交易凭据 |
| 无干预行为 | 现有自动策略 | 复用同一自动策略语义 |
| 干预行为 | 原版本行为 | 本设计的管理权切换 |
| 发布身份 | 自己的 commit/schema/seed/tag | 自己的 commit/schema/seed/tag |
| 证据 | 自己的认证与 postflight | 自己的认证与 postflight |

不复制 Tokyo 的活动 Ticket、授权事件、运行身份或账本来初始化新账户。
迁移链在各分支内单向、无分叉；相同编号不能被视为相同语义，发布同时核对 commit、
schema 和产品身份。公共修复按独立提交移植并分别验证；不整分支反向合并人工语义。

### 3.2 事实归属

- **原始 Ticket**：首次系统入场、初始风险及冻结 ExitProfile，不可重写。
- **Aggregate + Trade Events**：该笔唯一管理权和生命周期 authority。
- **交易所订单/成交/持仓**：外部操作与实际数量依据；不根据 App 点击或聊天猜测。
- **当前观察投影及证据记录**：保存验证后的外部事实，不能自己授予交易权限。
- **风险占用投影**：只供准入使用，由同一对账事务更新；不是第二份仓位账本。
- **Owner Policy**：资本、策略、范围及 ENTRY 意图；接管不会修改全局 Policy。

沿用一条 Kernel 链，不增加独立交易机器人或第五个交易写入 Worker。

## 4. 管理权与生命周期模型

### 4.1 与生命周期正交的管理权

在 `TradeAggregate` 增加拟议字段：

| 字段 | 含义/约束 |
| --- | --- |
| `management_mode` | `AUTO / REVIEW_REQUIRED / MANUAL`，新 Ticket 为 AUTO |
| `management_revision` | 正整数，管理权有效变化递增 |
| `manual_takeover_event_id` | MANUAL 必填，指向本 Ticket 的接管事件 |
| `manual_takeover_detected_at_ms` | 系统确认时间，不等于 Owner 点击时间 |
| `external_action_at_ms` | 交易所提供时保存；无确切值则为空，不伪造 |
| `management_reason_code` | 具体证据类型或待确认原因 |
| `management_evidence_id` | 可复核且不可改写的观察证据引用 |

**MANUAL 永远不能回到 AUTO 或 REVIEW_REQUIRED**；后续事实不全通过单独的
事实健康状态表示，不丢失已确认管理权。原始 Ticket 不新增可变管理权字段。

### 4.2 状态迁移

| 原状态 | 条件 | 结果 |
| --- | --- | --- |
| AUTO | 自身命令/自然成交完整可解释 | AUTO，原自动行为 |
| AUTO | 已核实外部新增/修改/撤销/减仓 | MANUAL，整笔接管 |
| AUTO | 历史不完整、归属矛盾、保护变化原因未知 | REVIEW_REQUIRED，停止该笔新自动处置 |
| REVIEW_REQUIRED | 后续完整事实证明全部为自身或自然变化，期间无外部干预 | AUTO，可恢复原路径；追加澄清事件 |
| REVIEW_REQUIRED | 取得外部干预证据 | MANUAL |
| REVIEW_REQUIRED | 仍不能解释 | 保持，通知，不用超时猜测 Owner 意图 |
| MANUAL | 任何后续观察/改回原值/进程重启 | MANUAL，直到终态也保留历史标签 |

待确认不是“人工接管后交回”；只有尚未被证明接管的交易才能通过证据澄清恢复 AUTO。

### 4.3 人工仓的生命周期

新增最小状态：`MANUAL_OPEN`、`MANUAL_FLAT_PENDING_ORDERS`。
事实不全通过独立的 `facts_health=complete/stale/gap/contradictory` 表达，
不再新增同义的 MANUAL_FACTS_PENDING 生命周期状态；MANUAL 管理权不变。

正常人工分支：

```text
MANUAL_OPEN
-> 实际部分退出/订单更新，仍为 MANUAL_OPEN
-> 数量归零且仍有挂单：MANUAL_FLAT_PENDING_ORDERS
-> 仓位零、关联订单均终态、无未决自身命令
-> SETTLEMENT_PENDING -> REVIEW_PENDING -> TERMINAL
```

终态仍写现有 Owner 投影与基础 Review。缺少退出成交明细时使用现有明确 unavailable
语义，不编造价格或收益，不把普通人工全平标为工程故障。不能调用带自动撤单副作用的
旧 `ExternalFlatDetected` 路径冒充人工终结。

### 4.4 首次保护之前

普通接管入口开放于初始止损已确认后，不要求等待 TP1 成交。
初始下单/部分成交/保护失败沿用现有安全处理；不得因这段阶段尚未完成就宣称已交付。
如果此前就观察到外部操作，进入交付待核实，停止不适用的原数量命令，重新读真实事实。
初始止损失败且仓位未被保护时，保留交付前安全退出职责；不据此获得人工接管后的
自动退出权限。该异常路径需独立测试，不能用旧完整仓位盲目补单。

## 5. 外部操作事实与识别

### 5.1 订单与成交模型

新增冻结的 `ObservedOrderTerms`、`ObservedFill`、`ManagementObservationBatch`：

- 订单精确身份：venue/account/instrument/position_side、regular/conditional namespace、
  exchange_order_id、client order ID、条件单与实际执行订单关联。
- 条款：order type、side、price、trigger price、original quantity、executed quantity、
  reduce-only/close-position语义、trigger price type、time-in-force、有效状态。
- 时序：exchange update/event time、接收时间、来源版本/序号、查询窗口及分页游标。
- 成交：唯一 trade ID、order reference、数量/价格/费用、成交时间；已收集同 ID 不重复入账。
- 完整性：所查询普通/条件订单与成交历史是否完整，是否截断、失联或序号断档。

金融数值使用 Decimal；缺失字段不默认零/false，namespace 不混用。
建立标准化条款摘要，排除普通累计成交量/更新时间变化带来的假“改单”。
触发后的条件单不能因原 algo ID 消失而被误判为 Owner 撤单。

### 5.2 必须先核实的交易所能力

**当前挂单轮询不足以证明“只要动过即接管”。**创建后立即取消、同 ID 改价后改回，
两次快照可能相同。必须在正式实现前核实普通单和条件单的更新事件、修改历史及
终态历史的实际覆盖，记录支持字段、保留期限、分页、速率与重连语义。

技术方向：Reconciliation 进程拥有账户订单更新订阅（若交易所支持）和有界 REST补采，
使用持久化游标与去重。事件流负责及时发现，REST负责对照和补采；两者都不是下单接口。
具体接口名、SDK及消息类型在能力验证后冻结，本文不虚构供应商保证。

若任一合法 App 操作无法被可靠观测，**不得静默降级成“等成交才接管”并宣称完成**。
该动作的覆盖是实现验收缺口，需记录具体限制后停止本功能发布；不新增人工确认流程
来掩盖能力不足。交易所不提供某历史变化时不可用当前快照“证明从未改过”。

### 5.3 自身动作归因

以 durable Command 的精确身份、意图条款、结果和订单关联为证据，不仅检查 `brc-` 前缀。

| 变化 | 判断 |
| --- | --- |
| 已核实自身 ENTRY/TP1/止损成交及匹配条件单触发 | 自动事件 |
| 自身改单或撤单与命令结果及条款完全匹配 | 自动事件 |
| 原系统订单 ID 未变，但非自身命令解释的条款变化 | 外部干预 |
| 外部新增退出挂单，未成交 | 外部干预 |
| 外部减仓成交，可精确归属当前 Ticket | 外部干预 |
| 确认取消，无自身取消、触发或交易所规则可解释，历史覆盖完整 | 外部干预 |
| 仅缺单、未知执行结果、交易所强平/自动过期、字段不完整 | 原因待核实，不冒充人工动作 |
| 实际增仓、反手、新仓或非退出挂单 | 范围外变化；停止自动旧仓处置与受影响准入，不吞入原 Ticket |

匹配窗口从本次 Ticket 初始入场延续到其订单清理完成。无当前归属的外部订单不强行
分配到最近一笔；持久化账户范围外障碍，并禁止受影响标的准入。

### 5.4 采样与恢复

- 单个账户游标加每标的/namespace补采游标，覆盖两方向及外部未成交订单。
- 所有网络 I/O 在 PG 事务外；完成一批后原子保存规范化证据、游标和投影。
- 去重键优先交易所事件/trade ID；无可靠ID时使用标准化身份+版本+摘要，并验证冲突。
- 不以本地时间覆盖交易所事件顺序；迟到旧事件不能覆盖新投影，但可揭示更早的人工干预。
- 重连先恢复历史完整性；未补齐前，不继续该笔自动处置，不扩张新准入。
- 只有明确无外部干预的完整历史才能解除 REVIEW_REQUIRED。
- 正常无变化采样只更新必要 current freshness/游标，不逐 tick 增长 Trade Events 或文件。

## 6. 持久化与事务

### 6.1 拟议物理设计

| 对象 | 存放位置 | 权威和约束 |
| --- | --- | --- |
| 管理权 current | 扩展 `brc_trade_aggregates` | 唯一 current，CAS revision；MANUAL不可逆 |
| 接管/澄清/人工变化 | 复用 `brc_trade_events` | append-only，同Ticket sequence、精确证据引用 |
| 订单 current | 新 `brc_ticket_external_orders_current` | ticket + venue namespace + order ID；保存自身/外部来源与条款 |
| 变更证据 | 新 `brc_external_order_observations` | 去重、不可变、仅状态变化，不存凭据和无关原始响应 |
| 事实完整性游标 | 新 `brc_account_observation_cursors` | account/instrument/namespace/source唯一；版本和覆盖窗口 |
| 人工风险占用 | 扩展现有 Reservation 当前事实，或经其统一仓储计算 | 不创建第二个资金池，不改冻结 Claim/Ticket |
| 标的占用锁 | 拟议 `brc_instrument_occupancy_current` | venue/account/instrument唯一，绑定原Ticket；两方向共用锁 |

表名是技术提案。字段、索引、最小权限和 migration 编号在实施M1冻结；不得修改已执行
历史迁移。运行时不兼容读取旧 schema，不设置缺列回退。

观察证据按 `evidence_kind=order_change/fill/position/coverage` 类型化保存；成交使用
venue/account/instrument/trade ID 的唯一约束，不以时间戳单独去重。
订单条款修订需保存前后摘要与完整规范化字段，摘要不能替代可核实的事实。

订单 current 和观察证据可保留闭合历史；runtime查询必须使用精确Ticket、active状态、
标的索引和有界窗口，不能每轮扫描所有历史订单。

### 6.2 接管事务

```text
取得事务外采集的完整证据
-> 按统一锁序读取账户风险、标的占用、Aggregate及相关Commands
-> 检查版本、证据身份/时效、管理权
-> 去重写入证据
-> 追加 ManualTakeoverConfirmed
-> 更新 management_mode=MANUAL 和该笔人工状态
-> 终结明确尚未发送的自动命令为 superseded，不调用交易所撤单
-> 同步仓位/挂单/风险健康投影与monitor
-> 提交
-> 事务外发一次接管通知
```

初始通知应列出实际剩余数量、现存 TP1/止损和接管原因；不得声称替 Owner 撤单。
同一证据重复接收不重复接管、不重复解锁、不重复告警。
管理权更新、命令禁止状态和Owner投影必须同事务；写一半回滚或完整提交。

### 6.3 读写权限

Domain纯模型无SQL/网络；Application用例；Infrastructure数据库和交易所适配。
复用UnitOfWork和事件提交路径。Owner API只读展示管理权，不提供“交回自动”接口。
任何身份不一致或新schema未就绪，Worker不得通过默认AUTO继续写交易所。

## 7. 自动写入限制与现有路径接入

Owner不要求讨论人机同时操作，本设计不增加操作前暂停流程，也不承诺点击瞬间零延迟。
但管理权已经持久化为MANUAL之后的权限必须可验证，不能只在UI隐藏按钮。

统一 `may_mutate_ticket` 判定用于：

1. Lifecycle 生成新 effects之前。
2. Command claim和实际发送前的现有适用性检查。
3. Reconciliation结果处理，尤其旧命令结果导致新撤单、补保护的分支。
4. Selection Vacuum drain、controlled exit、post-fill风险处置与orphan cleanup。
5. Owner Console 的flatten-all和单笔退出入口。
6. 部署drain与修复工具，不能绕开人工管理权强制平仓。

| 对象 | MANUAL下处理 |
| --- | --- |
| 明确未发送的 prepared/claimed命令 | 持久化superseded，无交易所动作 |
| 已开始发送或结果未知命令 | 只查真实结果，不盲重发，不因结果派生后续自动写入 |
| 交易所现存订单 | 原样保留，不撤销、不重新定价 |
| 原TP1后续成交 | 同步数量和资金，不自动挂保本或Runner保护 |
| 旧stop自然成交 | 只读收尾，不自动清理Owner挂单 |
| 重启后的旧任务/回调 | 先核对管理权，再应用结果；MANUAL不可回退 |

禁止把“结果未知”标为未发送来释放全局ENTRY lane。Lane仅在初始命令真相闭合后按
现有规则释放；管理权接管不创造第二次ENTRY，也不吞掉未知结果。
若原自动链在TP1命令生成时释放Lane，人工接管恰好阻止该步骤，则新增明确的
“初始ENTRY真相已闭合、保护已确认、无未决入场”释放分支，不能等待永远不会发生的
TP1来释放Lane。此动作只释放串行入场Lane，不释放该笔预算和标的占用。

新控制中心的“全平”不得暗中处置MANUAL Ticket；应返回明确的跳过项，提示到App处理。
这不是新增接管入口，是遵守已批准的“后续由Owner在App管理”。

## 8. 人工仓只读对账与终结

### 8.1 数量与订单

- 实际减仓以trade ID/订单真相为主；持仓快照用于验证，不用差值编造成交价格。
- 部分成交后更新剩余数量，不能要求等于原TP1目标，不自动调整任何挂单。
- 先按成交序列更新，再与同一覆盖窗口末尾的持仓核对；多次操作可一次补采。
- 暂时数量不一致保留待核实，不能把未知差异直接当人工盈利或新仓。
- 保护覆盖按当前订单条款显示；条件触发、close-position及两方向规则必须真实解析。
- 自动模式自身TP1部分成交沿用被验证的异常策略，不把旧partial-TP1缺陷伪装成Owner接管。

### 8.2 全平和残留

仓位为零但存在普通/条件退出挂单：保留MANUAL与标的占用，显示待Owner清理。
若订单列表分页截断或查询失败，不等于零挂单。不能只查程序client ID前缀而遗漏Owner挂单。

确认零仓、关联订单终态、无未决自身命令后：执行无交易所写入的settlement，释放
Reservation及标的占用，写基础Review和Owner终态投影。完整终态采用同一短事务，
经济明细暂缺遵循既有显式缺失路径，不凭空算零收益。

新交易只从新的合法Signal/Episode进入；退出事件不得重置旧信号消费标志。

## 9. 预算与同标的双向禁入

### 9.1 账户风险

自动和人工仓共同占用同一个新账户预算，人工接管不改变资金池或Policy。
首版技术选择为保守占用：

- 原初始风险额 `R0` 与初始实际成交数量 `q0` 冻结；人工当前数量 `q` 只允许减少。
- 若保护完整且可解释，当前占用不低于 `R0 × q/q0`，并与实际剩余止损风险取较大值。
- 当前止损风险以剩余数量、实际持仓成本、止损价及现有费用/滑点约束计算；
  止损在盈利侧不产生负预算抵扣，拉远止损可能增加占用。
- 多档保护需证明数量分配和方向/触发语义，不能把多个重叠全量止损简单相加当覆盖。
  首版无法证明分配时标记风险未知并阻断新增，而不是使用低估值。
- 更紧止损不能把名义保本变成零风险无限开仓；部分真实减仓可以减少保守占用。
- 保证金使用实时账户值与现有预留约束的保守组合，避免真实仓位与Reservation重复累加。
- 缺失/过期事实、实际增仓、保护不完整或无法归属时，禁止新增自动开仓；
  不动人工仓，不停止其他自动仓已有保护和退出。

这是实现中的计算方法，不增加Owner风险限额；M5须用数值用例证明不会低估、负值、
重复释放或凭移止损无上限释放。

### 9.2 双向禁入

新增准入键为 `venue + account + instrument`，不替换原精确side身份。
从Claim、Ticket最终签发直到ENTRY最终发送，均核对：

- 任何方向的非终态Ticket、人工仓、未决命令、实际持仓、占用及可能影响该标的的外部订单。
- 相反方向为空也不能忽略未成交的开仓单或残留条件单。
- 同一标的不能由不同策略并发分配到多空两笔；使用数据库唯一占用及锁，不靠UI检查。
- 已归零但挂单残留继续阻断该标的；未知账户风险可阻断整个账户新增。
- 保持交易所独立多空/Cross等现有能力，不用单向模式代替软件准入。

相同side不补仓、每Episode一Ticket、一次ENTRY generation、全局新ENTRY串行均保持。

## 11. API、前端和通知

现有当前持仓/历史交易DTO扩展：管理方式、接管确认时间、原因、事实健康、
当前剩余量、实际保护覆盖、仍有效退出订单、影响新开仓的具体原因。
初始Ticket数量/止损与当前人工条款分开显示，不能用原始stop冒充现有保护。

显示用语：自动管理 / 接管待核实 / 人工管理 / 已平仓待清理订单 / 已结束。
原自动TP1/Runner信息在AUTO保留；MANUAL显示当前订单事实，不提示“程序将移动止损”。
不提供恢复自动管理按钮，不为人工接管索要TOTP；既有Policy控制认证保持。

通知按ticket+状态版本去重：初始保护确认、接管确认、关键风险变化、风险解除。
一笔接管通知说明“整笔已转人工，现存挂单仍有效”；修改后的每次普通条款变化不刷屏。
复用已配置通知通道，不在本任务中修改凭据或发送测试消息。

## 12. 数据演进与部署

1. 仅新产品分支新增前向revision，编号按实施时head选择，不篡改共享历史迁移。
2. 自动历史初始化为AUTO，不能把历史外部变化推断为曾人工接管；没有运行历史的新账户
   走干净安装，不导入Tokyo运行数据。
3. 后续升级必须停止相关写入者并通过现有flat/preservation门槛，包含人工仓与外部挂单。
   人工仓非空时等待Owner自行处理，不用部署drain强平。
4. 管理权事件、订单证据和占用参与保全，未知结果不可因迁移被清空。
5. 新产品身份必须进入机器标记、数据库seed与发布校验，不能只凭分支名防止错部署。
6. 新服务器部署入口不得默认指向Tokyo；旧脚本硬编码目标/路径须在实施中显式参数化并测试，
   不用临时shell替代认证发布门槛。
7. Kernel及schema按R4认证，Owner API和前端分别执行需要的R2/R1认证。
8. 初次投产保持ENTRY关闭；配置与Owner意图由新账户正式路径建立，不复制旧授权。
9. 回退只可在无新schema写入且合同允许时恢复原制品；进入新schema后采用fix-forward，
   不让旧代码带人工状态继续运行。不迁移活动人工仓到Tokyo。

新产品首次部署时，在本产品分支的既有主路线图位置记录新环境事实，标明产品与目标；
继承的Tokyo状态仅作历史参照，不能同时冒充新环境当前事实。Tokyo分支自己的主路线图
不随此变更；不随意增加 `docs/current` authority文件。发布记录和产品标识必须相互对应。

本设计不构成部署或实盘验收授权。当前任务只编写文档。
